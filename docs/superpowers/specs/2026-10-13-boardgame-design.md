# 大创造时代联机网站第一版设计

日期：2026 年 10 月 13 日

状态：用户已确认本设计，可作为开发计划依据。

建设一个面向公众、免费创建和加入房间的桌游网站，先支持《大创造时代》，随后再考虑《神秘大地》及扩展。核心体验是玩家随时上线走一步，系统保存局面、执行规则并完成计分。电脑体验优先，手机适配不阻塞首个测试版本。

技术上具备实现条件。最大的开发工作是规则及能力组合的正确性、异步响应顺序和复杂局面的操作界面。当前结论是设计层面的可行性判断，还没有通过可运行原型验证规则覆盖、性能或成本。

## 已确认的产品范围

| 项目 | 已确认的方向 |
| --- | --- |
| 使用人群 | 面向公众，支持陌生玩家组局 |
| 收费 | 玩家免费创建和加入房间 |
| 首款游戏 | 大创造时代本体，目标是完整多人对局 |
| 后续游戏 | 神秘大地及扩展，独立安排开发 |
| 游玩节奏 | 异步对局；玩家同时在线时也可以连续操作 |
| 规则处理 | 系统校验行动、结算资源和分数 |
| 蹭魔 | 玩家设置自动接受条件，条件外等待本人选择 |
| 设备 | 电脑优先，逐步完善手机操作 |
| 找人方式 | 公开房间列表，以及私密房间邀请链接 |
| 记录 | 保存局面、操作历史和最终结果 |

第一版不包含排位、赛事、AI 对手、站内语音、自定义房规或其他游戏。单人自动机不属于本次多人版本范围。开发期间允许用有限能力组合验证，但这种原型不能作为完整本体版本交付。

## 实现路线

采用专注于首款游戏的自动规则网站。账号、房间和对局存储可以复用；《大创造时代》的规则单独实现，后续游戏拥有各自的规则模块。

半自动桌面虽然减少部分规则编程，却会把合法性检查、资源调整和争议处理交给玩家，不符合本项目希望提供的异步自动体验。先建设通用多桌游引擎会增加初期抽象和验证成本，因此不作为第一版路线。

## 第一版默认行为

以下默认行为随本设计一并确认，后续需求变更须同步更新设计与实现计划。

| 问题 | 建议默认值 |
| --- | --- |
| 界面语言 | 简体中文，术语在规则整理阶段统一 |
| 首版人数 | 支持本体 2 至 5 人的多人规则，不含自动机 |
| 行动期限 | 默认不设置强制超时，不替玩家自动行动或判负 |
| 长期未完成的对局 | 保留局面；玩家可从个人列表隐藏，隐藏不影响其他人或删除对局 |
| 提醒方式 | 站内待行动列表与标记；首版不依赖邮件、短信或浏览器推送 |
| 操作撤回 | 提交前可修改；服务端确认后的行动首版不支持回退 |
| 自动蹭魔 | 默认关闭；玩家按每局设置，可接受实际扣分不超过其阈值的规则允许选项，超出条件等待本人决定 |
| 自动蹭魔更新 | 新设置应用于尚未处理及后续产生的响应，已完成的响应不重算；变更及处理结果保留记录 |
| 对局可见性 | 房间列表仅展示招募信息；局面和详细记录由本局玩家访问，首版不开放观战 |
| 开局 | 全员准备后由房主启动；启动后固定参与者，不支持中途换人或加入 |
| 开局配置 | 首版提供一种按官方规则实施的标准开局，不提供自定义设置编辑器 |

若规则允许多种接受方式，自动蹭魔选择必须唯一、合法且符合玩家设定；不能确定时交回玩家。其他策略选择不自动代办。准确选项及结算顺序以规则核对结果为准，不根据“通常如此”推断。

## 页面与用户流程

玩家注册或登录后进入首页，看到待自己操作、等待他人和已结束的对局。首页同时提供创建房间和浏览公开房间的入口。

房间页展示人数、参与者和准备状态。私密房间通过不可猜测的邀请链接加入；座位与账号绑定。开局流程由系统引导玩家完成选择和摆放，不能跳过规则要求的步骤。

电脑对局页以地图为中心，附近展示当前玩家资源、公共行动、轮次与计分条件。其他玩家信息可展开查看。行动区域明确写出当前需要谁作出什么选择；历史记录显示行动、资源变化及自动处理结果。

涉及多个选择的行动先进入本地草稿，展示已确定的成本和效果，再由玩家提交。需要后续响应或选择的效果明确标注，不把尚未确定的结果显示为已经发生。

手机采用可缩放地图与可切换面板，保留全部必要操作入口。首个电脑测试版本可以先采用基本移动布局；完善手机体验是后续同项目工作，不重新设计另一套游戏规则。

结束页展示最终分数明细和操作历史。第一版提供按时间查看记录，不包含任意局面跳转、分支推演或复盘分析工具。

## 系统组成与行动处理

采用浏览器界面、单个后端应用和关系型数据库的简单结构。游戏状态只在处理行动时推进，不需要为每个等待中的房间持续运行计时循环。初期不引入微服务或独立房间服务器。

后端中的规则模块只接收当前局面和行动，返回新局面、效果记录及下一步需要的选择。它不依赖网页界面，可以单独进行规则测试。账号、房间、通知和数据库访问由其他模块负责。

一次提交按以下顺序处理：

1. 校验账号、座位、当前局面版本及行动权限。
2. 校验资源、目标、回合阶段和具体能力限制。
3. 按规则处理效果，产生需要玩家决定的响应。
4. 在同一数据库事务中保存新局面、操作记录及提交标识。
5. 保存成功后确认提交，并通知在线玩家获取最新局面。

浏览器不能直接写入最终资源或分数。每次提交携带唯一标识与局面版本，避免网络重试导致重复扣费，也避免电脑和手机同时操作覆盖彼此。

界面更新通知只负责告诉玩家有变化，数据库中的已保存状态才是依据。连接断开后重新获取最新状态；错过通知不会导致行动丢失。草稿基于旧版本时要求刷新并重新确认，不能静默套用到新局面。

## 异步对局与中途响应

系统区分开局选择、正常行动、待响应、轮次结算与结束等阶段。当前需要操作的人可能是非当前回合玩家，例如需要决定是否蹭魔的人，因此“轮到我”的判断必须包含所有待处理选择。

凡是后续行动依赖前一响应的结果，都等待该响应完成后再推进。不能为了加快异步对局而改变规则结算顺序。是否存在能够安全并行的响应，要经官方规则确认和测试后才可采用；初版优先明确顺序。

符合个人设置的蹭魔由服务器按同一规则路径执行，并记录触发原因、设置条件、实际获得的魔力和扣分。自动行为与手动行为使用相同的合法性校验。

玩家离线时保留待处理选择，服务器重启后仍可恢复。错误或不合法的行动不改变局面，返回可理解的原因；确认保存之前，界面不能声称行动已经成功。

## 规则版本与内容覆盖

建议以官方本体规则加官方已发布的种族修订作为首版依据。发行商说明，2024 年 9 月修订了三个种族，并从实体版本 1.2 起纳入这些调整。具体中文术语须与采用的中文版本核对。[官方游戏页及修订入口](https://www.feuerland-spiele.de/spiele/age-of-innovation/)

开发规则模块前，建立逐项覆盖表，包含规则来源、触发条件、合法输入、资源变化、后续响应与验证案例。覆盖地图与相邻关系、地形改造、建筑与升级、魔力循环、学科与书籍、创新及其他能力、城市、收入、轮次与终局计分、开局和人数差异。

官方资料说明本体包含多种可组合的种族、地形与能力，组合覆盖是主要验证工作之一。[发行商介绍](https://capstone-games.com/products/age-of-innovation/)

每局创建时记录规则版本及实际开局配置。部署新规则时保留旧局所需版本；只有经过兼容性验证的修复才可应用到进行中的对局，不能直接用新的平衡设置改变旧局。

## 验证与完成标准

| 验证对象 | 首版应达到的结果 |
| --- | --- |
| 规则 | 基础动作、每项能力及关键组合有来源和有意义的案例；资源与阶段始终合法 |
| 完整对局 | 2 至 5 人各人数配置能够从准备、开局推进到最终计分，包含对应规则差异 |
| 蹭魔与响应 | 测试自动接受、等待本人、修改设置、连续触发及离线恢复，不遗漏或重复执行 |
| 提交可靠性 | 重复提交、过期局面、双端同时操作与非本人操作均得到明确处理 |
| 数据恢复 | 保存成功的行动在刷新、断线和后端重启后仍存在；备份能够实际恢复 |
| 界面 | 电脑端可以完成所有必要操作；手机端验证地图和行动入口，再逐步完善布局 |
| 玩家试局 | 熟悉游戏的玩家完成多轮试局，核对结算与特殊能力；不以页面演示代替真实对局验收 |

性能测试使用预先写明的在线人数、活跃房间数、行动频率及历史数据量，记录响应时间、错误率和资源占用。没有测量前，不承诺某台服务器能承载多少玩家。

## 开发顺序与可行性

第一阶段完成规则来源与覆盖表，用固定开局和少量能力组合跑通完整轮次流程。优先验证地图行动、资源变化、异步响应与结算；这是减少后续返工的关键。

第二阶段接入多人房间、账号、持久化和断线恢复，通过多个浏览器会话完成一局。此时仍属于受限测试版本。

第三阶段补齐本体能力、人数差异与官方修订，完成规则覆盖检查和真实玩家试局，达到完整本体测试版要求。

第四阶段完善公开房间、账号日常使用、手机布局、备份恢复和部署验证，为公众使用做准备。手机体验继续服从电脑优先的顺序。

回合制让服务器无需高频计算每局状态，因此小规模起步可以采用简单部署。但免费游玩仍会产生服务器、数据库、备份和维护成本。预算与目标规模尚未给出，现阶段不把“压力可能较小”换算成固定价格或工期；在首个联机版本测量后再估算。

公开发布还涉及数字改编及名称、美术和文字素材的使用许可，需要向权利方确认适用条件。当前未核实相关许可；开发原型可以先使用自制占位图形，技术可行性结论不代表发布许可已经落实。

## 后续工作

产品范围、默认行为和系统设计已在对话中确认。下一步据此制定具体实现计划，选择技术工具及其版本，并为首个可验证阶段安排开发任务。
